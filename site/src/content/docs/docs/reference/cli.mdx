```
cratebase serve                                   # start the server
cratebase serve --dev --automigrate=false         # verbose logging + hook reloading; don't write migration files

cratebase superuser create <email> <password>     # headless first-superuser (or any additional one)
cratebase superuser update <email> <password>
cratebase superuser upsert <email> <password>     # create or update, whichever applies
cratebase superuser delete <email>
cratebase superuser otp <email>                   # print a one-time OTP code/id, for a locked-out dashboard

cratebase migrate up                              # apply every pending migration (core + pb_migrations/*.js)
cratebase migrate down [n]                        # revert the last n (default 1) from each history
cratebase migrate create <name>                   # scaffold a pb_migrations/<timestamp>_<name>.js stub
cratebase migrate collections                     # snapshot every current collection into a migration
cratebase migrate history-sync                     # drop ledger rows whose migration file no longer exists

cratebase schema pull --out schema.json           # snapshot the live schema to a JSON file
cratebase schema push schema.json [--dry-run] [--force]   # apply a schema-as-code file's diff

cratebase plugin install <path>                   # install a local WASM plugin
cratebase plugin list

cratebase seed <path> [--upsert]                  # populate collections from *.json/*.js seed file(s)
cratebase reset [--yes]                           # wipe the SQLite database and re-run migrations

cratebase migrate-from-pocketbase <pb_data> --dir <dir>   # one-shot PocketBase import
cratebase typegen [-o path]                       # write TypeScript types for the local schema
```

See [JavaScript hooks](/docs/extending/js-hooks/#migrations) for what
`migrate up`/`down`/`create`/`collections`/`history-sync` actually do,
and [Schema as code](/docs/extending/schema-as-code/) for `schema
pull`/`push`.

## `seed` / `reset`

`cratebase seed <path> [--upsert]` bootstraps the target database (like
any other command here) and applies `path` — a JSON seed file, or a
directory of `*.json`/`*.js` seed files — through the same
create/validate path the HTTP API uses (never raw SQL), so an auth
collection's `password` is hashed exactly like a real create and a bad
record is rejected exactly like a bad request would be. `path` is always
an explicit argument; `CB_SEED_DIR`/a `pb_seed/` directory next to the
data directory is only the convention the (forthcoming) `cratebase dev`
auto-seed uses. See [Seeding data](/docs/getting-started/first-run/#seeding-data)
for the file format, `--upsert`'s idempotency guarantee and the
transaction/rollback behavior on an invalid record.

`cratebase reset [--yes]` deletes the SQLite database files under the
data directory — the main database (and its `-wal`/`-shm` sidecars) and
the auxiliary logs database — then re-bootstraps (recreating system
tables and re-running every core migration) and re-applies every JS
migration in `pb_migrations/`, leaving a schema-only, empty database.
This is destructive and requires confirmation: without `--yes` it prints
exactly which files it's about to delete and asks for a typed `yes` on
stdin; `--yes` skips the prompt for scripted use (a fresh CI database, a
local reset-and-reseed loop). It refuses outright — before deleting
anything — when `DATABASE_URL` is a Postgres connection string: dropping
every user collection and system table in a database this tool did not
provision and cannot safely recreate is too destructive to automate
here. Reset a Postgres database by hand (`dropdb`/`createdb` or your
platform's equivalent) and run `cratebase migrate up` afterward.

Flags generally mirror their environment-variable equivalents (e.g.
`--dir` vs `CRATEBASE_DATA_DIR`); an explicit flag on the command line
wins over the environment variable when both are set for the same
option — except `serve --dev`/`--automigrate`, which fall back to
`CB_DEV`/`CB_AUTOMIGRATE` (rather than each flag's own hard-coded
default) whenever the flag itself is left off the command line, so
setting only the env var still works.

## `cratebase typegen`

Writes a `.d.ts` file with the local data directory's schema, using the same generator as
`GET /api/typegen` and the `--dev` `CB_TYPEGEN_OUT` watch — see
[Generating TypeScript types](/docs/extending/schema-codegen/) for the full field mapping and the
`Schema`/`SchemaCreate`/`SchemaUpdate` shape.

```
cratebase typegen                    # writes ./cratebase-types.d.ts
cratebase typegen -o types.d.ts      # writes to a named file
cratebase typegen -o -               # writes to stdout
cratebase typegen --dir ./pb_data    # read a different data directory
```

- `-o, --out <path>` — output path, or `-` for stdout. Default: `./cratebase-types.d.ts`.
- `--dir <path>` — data directory (same default and `CRATEBASE_DATA_DIR` precedence as every other
  subcommand).
