```sh
cratebase serve
```

starts listening on `:8090` immediately — SQLite database and data
directory are created on first run, there is nothing to provision ahead
of time.

## The inline setup form (no CLI required)

`cratebase serve`'s startup log prints a one-time install token and a
ready-to-open dashboard URL, something like:

```
no superuser exists yet — open this URL to create the first admin account
url=http://127.0.0.1:8090/_/login?token=Ab12Cd34...
```

Open that URL. `GET /api/setup/status` reports `{"needsSetup": true}`
until a superuser exists, and the dashboard renders an inline
superuser-creation form instead of a bare login screen. Fill it in —
email + password — and `POST /api/setup` creates your first
`_superusers` record and logs you straight into the dashboard.

The token in that link matters: without it (or with the wrong one),
`POST /api/setup` is a flat `403` — a freshly deployed public instance
isn't up for grabs by whoever finds the port first, only by whoever can
read the boot log (or was handed `CB_SETUP_TOKEN` for a scripted
deploy). Opening `/_/login` with no `token` in the URL at all shows a
message pointing back at the log instead of a form nobody can submit.

This is also a one-time, self-closing endpoint regardless of the token:
once a superuser exists, `POST /api/setup` is permanently rejected, from
either the form or a direct API call.

## Headless / scripted setup

Prefer not to click through a form (CI, a Docker entrypoint, a
first-boot script)? Create the superuser directly — no token needed,
since this never goes over HTTP:

```sh
cratebase superuser create you@example.com yourpassword
```

Both paths are race-safe: the dashboard's `POST /api/setup` re-checks
"does a superuser exist" and inserts inside one write transaction (an
advisory lock on Postgres, since SQLite's single writer already
serializes it), so however many setup requests arrive at once, exactly
one succeeds and the rest see the same `403` a second, later `superuser
create` would.

## Verification, password-reset and OTP mail

No SMTP server to configure before you can try any of this: a fresh
instance's `smtp.enabled` defaults to `false`, which routes mail through
a zero-config `Log` backend instead of failing or silently dropping it.
Every email it "sends" — a signup verification link, a password-reset
link, a one-time login code — lands in an in-memory dev inbox you can
browse superuser-only at `GET /api/dev/mails`, or in the dashboard under
**Settings → Mail inbox** (next to **Mail & storage**, which only appears
while `Log` is actually in use). Click through the rendered HTML — links
open in a new tab — or read the plain-text alternative; either way the
token is right there, no real mailbox required. Turn on real SMTP later
(`smtp.enabled: true` or `SMTP_HOST`/`SMTP_ENABLED`, etc. — see the
[configuration reference](/docs/deploy/configuration-reference/)) and
the dev inbox — and its routes — disappear.

## Data directory layout

By default Cratebase writes to `./data` (override with
`CRATEBASE_DATA_DIR` or `cratebase serve --dir <path>`):

```
data/
├── data.db          # the primary SQLite database (or unused if DATABASE_URL points at Postgres)
├── data.logs.db      # request/audit log, kept in a separate file so logging never takes the writer lock
└── storage/          # local file storage (uploads), unless S3-compatible storage is configured
```

A `pb_hooks/` directory placed next to the data directory (or pointed at
via `CB_HOOKS_DIR`) is picked up at startup for
[JavaScript hooks](/docs/extending/js-hooks/); its absence is a
complete no-op.

## Seeding data

`cratebase seed <path>` populates collections from a JSON file (or a
directory of them) through the ordinary record-creation path — the same
validation, relation checks and password hashing a real
`POST /api/collections/<name>/records` gets — instead of raw SQL:

```json title="pb_seed/01-users.json"
{
  "users": [
    { "id": "seeduser0000001", "email": "demo@example.com", "password": "supersecret123" }
  ]
}
```

```bash
cratebase seed pb_seed/
```

A `path` that's a directory applies every `*.json` file in it in
file-name order (`01-users.json` before `02-posts.json`), so a later
file's records can point relations at an id an earlier file seeded — a
supplied `id` is validated and kept, not discarded. Add `--upsert` to
make re-running the same seed idempotent (a record whose `id` already
exists is updated instead of failing on the collision); without it, a
rerun fails on the first duplicate id, since a seed is normally meant to
run once against a fresh database. The whole directory's `*.json` files
are applied inside a single transaction: an invalid record anywhere
rolls back everything the run had written so far, and the error names
the exact file, collection and record that failed. A `*.js` file in the
same directory is written like a migration
(`migrate((app) => { ... }, (app) => {})`) and its `up` runs once, with
`$app` available, but is never recorded as "applied" — see
[JavaScript hooks](/docs/extending/js-hooks/) for the `$app` API.

`cratebase reset [--yes]` wipes the data directory's SQLite database
files and re-runs every migration, for when local test data needs to
start over — see the [CLI reference](/docs/reference/cli/) for exactly
what it deletes and why it refuses a Postgres `DATABASE_URL` outright.
